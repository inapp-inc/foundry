The Core Workflow

Intent-Driven Development

Intent-Driven Development (IDD) is Foundry's core workflow — the focus is on capturing and implementing what the business actually needs, not just coding the feature as stated. SDD (the Method that follows) is the tool: it turns captured intent into specs, contracts, and audits, so the build stays provably tied to the outcome, not just the request.

Traditional requirement

"Build an approval screen with Approve/Reject buttons."

→
Intent-driven requirement

"Enable managers to approve employee requests within 2 minutes, from any device."

The second statement drives better decisions — about UI, automation, notifications, and mobile support — because it states the outcome the business needs, not just the screen to build.

SDD on its own
Requirements→ Design→ Code→ Test
Foundry's IDD workflow
Intent→ Outcome→ Design Options→ Code & Test — SDD→ Validate Outcome

SDD supplies the design, code, and test discipline once intent and outcome are set — it's the tool inside Foundry's workflow, not a competing one.

How Foundry Practices IDD
Outcome over output Success is measured by whether the user achieved the outcome — not by whether a checklist of screen elements exists and technically works.
"Why" before "what" Every requirement starts as a question about the business need. The screen, the workflow, the automation — those are answers, decided afterward.
Intent can evolve — the build follows Requirements aren't frozen before work starts. As the intent becomes clearer through Steps 1–11, the spec sharpens with it.
Built for AI Intent translates naturally into user stories, workflows, and code. That's exactly what makes fast turnaround possible — AI does the translating.
The real risk is misunderstanding, not overbuilding Building the wrong thing perfectly is a bigger failure than a rough edge on the right thing. Foundry optimizes against the first risk.
Intent, Translated by AI

A single intent statement is enough for an AI-enabled IDD process to generate the pieces a traditional spec would have had to enumerate by hand:

"I want managers to approve leave requests quickly from mobile devices."

Mobile-first UI Approval workflow Notifications Security rules APIs Test cases

No detailed specification comes first — SDD forms once the intent is captured, not before. That ordering is what "IDD is the workflow, SDD is the tool" means in practice.

Why It Matters

Four outcomes, not twenty-two steps

Foundry exists to produce one thing: a working business solution the client can trust, built fast. The Method below is how. These are why it works.

Speed with a floor under it

Turnaround is short because the path is already decided, not because steps get skipped. Nothing in the sequence below is improvised mid-engagement.

Built against the real intent

Gaps are closed and the outcome is validated before a line of code is written, so the team builds what the business actually needs — not just what was asked for.

Auditable, not just demoed

Every build is checked against its own source of truth, reviewed for intent, and cleared against OWASP before it ships. "Done" means something specific.

A handover the client can own

Documentation, architecture rationale, and a reusable scaffold ship with the code — so the client isn't locked into the team that built it.
